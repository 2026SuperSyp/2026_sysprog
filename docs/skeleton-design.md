## 1. 지금의 병목

지금 급한 것은 코드보다 약속이다. **나눠 줄 약속이 아직 닫혀 있지 않다.** v6 그대로 헤더를 배포하면 팀원이 만드는 도중에 막혀 헤더를 고쳐야 하는 곳이 있고, 코어 쪽에는 정하지 않은 채 코드를 쌓으면 나중에 갈아엎어야 하는 선택이 있다.

**어떻게 확인했나.** 전체 정리 문서를 처음부터 다시 읽으면서 스테이지, 화면, 서버와 클라이언트, 뇌, 보스전 순으로 "명세대로 만들면 어디서 막히나"를 따졌다. 아직 코드가 없어서 문서만 보고 판단한 것이다. 걸리는 곳은 세 종류였다.

| 종류 | 뜻 | 어디서 다루나 |
|---|---|---|
| 약속을 깨는 것 | 그대로 배포하면 팀원이 쓴 코드를 나중에 고쳐야 한다 | 아래 다섯 가지, 6장 |
| 틀을 정해야 하는 것 | 팀원 코드와는 무관하지만, 정하지 않고 코어를 쌓으면 갈아엎는다 | 아래 열 가지, 7~9장 |
| 지금 한 줄로 닫히는 것 | 나중에 고쳐도 되지만, 주석 한 줄이나 필드 하나로 오늘 닫는 편이 싸다 | 6.1의 표 |

**약속을 깨는 다섯 가지** (6장에서 고친다)

| 무엇 | 그대로 두면 |
|---|---|
| 이펙트 함수가 캔버스를 받는다 | 맞는 순간을 아는 `stage_tick`에는 캔버스가 없다. 완료 기준 6번을 네 스테이지가 제각각 우회한다 |
| 스테이지 전용 그림을 불러올 함수가 없다 | `.spr`을 만들어도 `ui_sprite`에 넘길 번호가 없다. 그림마다 헤더 변경 요청이 온다 |
| `brain_fired`의 뜻이 한 줄뿐이다 | "넘는 순간"인지 "넘어 있는 동안"인지에 따라 플래핑 플라이의 초파리가 바닥에 떨어지거나 천장에 붙는다 |
| 가짜 뇌와 진짜 뇌가 함께 지킬 반응이 없다 | 진짜 배선은 양쪽에서 다가오면 방향 전환이 꺼진다(전체 정리 18장). 가짜 뇌가 이를 흉내 내지 않으면 거미줄 미로를 11/26에 다시 짠다 |
| `make run`이 한 명, 키보드만 돌린다 | 유저별 상태를 나누지 않은 스테이지도 완료 기준을 전부 통과하고, 서버에 붙이는 날 한꺼번에 깨진다 |

**틀을 정해야 하는 열 가지** (7~9장에서 정한다)

| 무엇 | 정하지 않으면 |
|---|---|
| 스테이지 함수가 불리는 규칙(스레드, 순서, 횟수, 시간) | 담당마다 다르게 가정한다 |
| 스테이지를 돌리는 실행기 | 혼자 돌릴 때와 서버가 띄울 때 다른 코드를 탄다 |
| 스테이지가 그린 그림이 클라이언트까지 가는 길과 픽셀 형식 | 화면 라이브러리, 실행기, 서버, 클라이언트 네 곳이 이 위에 선다 |
| 뇌의 시간과 게임 틱을 맞추는 방식 | 화면 없이 빨리 돌리면 초파리가 한 번도 반응하지 않은 채 검사가 통과한다 |
| 통신 메시지의 틀과 소켓에 쓰는 주체 | 느린 접속자 한 명이 전원의 화면을 멈춘다 |
| 서버의 스레드, fork, 시그널 규칙 | 뇌를 다시 띄울 때 소켓과 파이프가 딸려 간다 |
| 게임 진행을 맡는 상태 기계 | 접속 끊김이나 스테이지 죽음을 처리할 자리가 없다 |
| 보스전의 입력과 위치의 주인 | 혼자용 3D를 여러 명용으로 다시 짠다 |
| 화면을 터미널 크기에 맞추는 정책 | 줄여서 보여 주면 1픽셀 벽과 글씨가 깨진다 |
| `make bot`의 "죽지 않는다"가 무슨 뜻인가 | 끝냈다고 한 스테이지가 검사를 켜는 날 떨어진다 |

**진짜 뇌의 속도는 따로 본다.** 가장 큰 위험이지만 `brain.h` 뒤에 있어서 틀을 바꾸지 않는다. 다만 11/23까지는 재야 한다(10장).

**일이 몰리는 곳.** 헤더, 코어, 뇌, 보스전, 결합이 모두 팀장 한 사람을 지난다. 팀원 두 명은 키트가 나올 때까지 시작하지 못한다. 그래서 순서는 약속을 먼저 얼리고(6장), 키트를 내고, 그다음 끝에서 끝까지 잇는다(10장).

## 2. 뼈대의 목적

뼈대는 게임이 아니다. 세 사람의 코드와 여러 프로세스가 맞물리는 자리다. 게임 내용은 앞으로 2주 동안 계속 바뀌겠지만, 맞물리는 자리는 한번 나눠 주면 바꾸기 어렵다. 그래서 뼈대에서는 "무엇을 만들까"보다 "무엇이 바뀌어도 되게 할까"를 먼저 정한다.

**목표**

| 번호 | 목표 | 됐는지 확인하는 방법 |
|---|---|---|
| G1 | 팀원이 자기 폴더만 고쳐서 스테이지와 화면을 끝까지 만든다 | 스테이지 폴더를 하나 새로 넣으면 다른 파일을 건드리지 않고 `make run STAGE=이름`이 돈다 |
| G2 | 나눠 준 약속(헤더, 파일 형식, make 명령)은 늘어나기만 하고 바뀌지 않는다 | 배포 시점의 예제 스테이지가 12/1까지 수정 없이 컴파일되고 돈다 |
| G3 | 혼자 돌린 스테이지와 서버가 띄운 스테이지가 같은 코드다 | 같은 실행 파일을 실행 방식만 바꿔서 띄운다 |
| G4 | 스테이지 코드는 가짜 뇌와 진짜 뇌를 구분하지 않는다 | 스테이지를 다시 컴파일하지 않고 뇌만 바꿔 실행한다 |
| G5 | 이틀 안에 접속부터 랭킹까지 한 줄기가 얇게라도 진짜로 돈다 | 봇 접속자 2명이 화면 없이 한 판을 끝까지 간다 |
| G6 | 화면을 띄우지 않고도 깨진 것을 안다 | 같은 씨앗과 같은 입력이면 같은 점수가 나오고, 이를 명령 하나로 돌린다 |

G5의 "이틀"은 전체 정리 27장의 11/21~22 통과 기준("2명이 접속해 예제 완주")과 같은 날짜다.

**하지 않는 것**

뼈대는 아래 항목이 들어갈 자리와 약속만 만든다. 내용은 만들지 않는다.

- 미니게임 4종의 규칙과 그림
- 보스전의 규칙과 3D 그리기
- 진짜 뇌 시뮬레이터
- 로비·결과·랭킹 화면의 디자인
- 속도 최적화
- 재접속(F9), 훈련 트랙(F10), 장치 입력(F7)

**돌아가더라도 실패로 보는 것**

- 배포한 뒤 함수 모양이 바뀌어 팀원이 이미 쓴 코드를 고쳐야 한다.
- 혼자 돌릴 때와 서버에 붙였을 때 스테이지가 서로 다른 코드를 탄다.
- 전체 결합을 11/28에 처음 해 본다.
- 스테이지를 추가하려면 Makefile이나 코어를 고쳐야 한다.
- 스테이지 안에 "가짜 뇌일 때"와 "진짜 뇌일 때"가 갈라져 있다.
- 실제 터미널을 눈으로 봐야만 깨진 것을 알 수 있다.

| 환경 | Ubuntu 24.04. 개발은 윈도우 노트북의 WSL2 | 2장, 14장 |
| 표절 | 공개 저장소 코드를 복사하면 F. 오픈소스에서는 데이터와 논문 수식만 쓴다 | 2장, 29장 |
| 최소 요건 | C 500줄, 시스템 콜 5종, 핵심 기능 3개 | 2장 |
| 날짜 | 기능 동결 11/30, 발표 12/1, 제출 12/20 | 27장 |
| 폴더 규칙 | 자기 폴더 밖은 고치지 않는다. 헤더는 팀장만 바꾼다 | 26장, A.2 |
| 스테이지 규칙 | 소켓, 스레드, fork, 파일 쓰기, 화면 직접 출력, 시계 읽기를 쓰지 않는다 | A.3.1 |
| 터미널의 한계 | 키를 뗀 순간을 모른다. 동시 키 입력이 약하다 | 11장 |

**팀장 노트북에서 확인한 것** (2026-11-21)

| 항목 | 값 |
|---|---|
| WSL | Ubuntu 24.04.4 LTS, WSL2, 기본 배포판 |
| 도구 | gcc 13.3.0, GNU Make 4.3, git 2.43.0, rsync 있음 |
| 자원 | 코어 8개, 메모리 15GB |
| 저장소 위치 | 윈도우 쪽 바탕화면. 경로에 공백, 대괄호, 한글이 들어 있음 |
| WSL에서 보이는가 | `/mnt/c/...` 경로로 보임. 모든 파일이 실행 권한이 켜진 것으로 보임 |
| 줄바꿈 | 윈도우 git은 `core.autocrlf=true`(시스템 설정), WSL git은 설정 없음 |

저장소 위치와 줄바꿈은 뼈대에 직접 영향을 준다. 경로에 공백과 대괄호가 있으면 Makefile의 절대 경로가 깨지고, 윈도우 git이 파일을 꺼낼 때 줄바꿈을 CRLF로 바꾸면 리눅스에서 읽는 설정 파일과 그림 파일 줄 끝에 `\r`이 붙는다. 대책은 8장에 적는다.

**확인하지 못한 것**

- 팀원 노트북 두 대의 WSL 상태
- Windows Terminal이 실제로 내는 프레임 수
- 노트북 여러 대 사이의 접속

## 4. 접근 방식

뼈대를 자르는 순서에는 세 가지 길이 있다.

| 길 | 내용 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| 가. 팀원 키트만 먼저 | 헤더, 화면 라이브러리, 가짜 뇌, 혼자 돌리는 실행기, 예제 스테이지를 먼저 배포한다. 서버·클라이언트·뇌 프로세스는 주말에 따로 만든다. 전체 정리 27장의 원래 순서 | 팀원이 가장 빨리 시작한다 | 혼자 돌리는 실행기와 서버가 띄우는 방식이 따로 만들어진다. "혼자서는 되는데 서버에서는 안 된다"가 뒤늦게 드러난다 |
| 나. 끝에서 끝까지 먼저 | 서버, 클라이언트, 스테이지 프로세스, 뇌 프로세스를 얇게 전부 이은 다음 배포한다 | 모든 이음매가 첫날부터 실제로 돈다 | 팀원이 하루 이상 더 기다린다. 이미 하루 밀렸다 |
| 다. 키트를 끝에서 끝까지의 첫 조각으로 | 스테이지를 감싸는 실행기를 처음부터 세 가지 방식(혼자, 봇, 서버가 띄움)으로 설계한다. 오늘은 앞의 두 방식만 채워 배포하고, 세 번째 방식과 서버·클라이언트·뇌 프로세스는 같은 실행기 위에 주말에 채운다 | 팀원은 오늘 시작한다. 약속은 배포 시점에 얼리고, 주말에 늘어나는 것은 전부 스테이지 코드 바깥이다 | 오늘 만드는 실행기가 조금 더 크다 |

**선택: 다** ★

이유는 2장의 목표 G1과 G3을 동시에 만족하는 길이 이것뿐이기 때문이다. "가"는 G3(같은 코드)을 포기하고, "나"는 G1(팀원이 오늘 시작)을 포기한다.

**검토하고 버린 것**

| 방식 | 버린 이유 |
|---|---|
| 프로세스를 나누지 않고 스레드만 쓰는 한 덩어리 서버 | 만들기는 쉽다. 하지만 fork, exec, pipe, 공유 메모리가 사라져 시스템 프로그래밍 요소가 줄고, 스테이지 하나가 죽으면 서버가 같이 죽는다 |
| 클라이언트가 스테이지 코드를 직접 돌리고 입력만 주고받는 방식 | 통신량은 적다. 하지만 모든 컴퓨터가 완전히 같은 계산을 해야 하고, 한 번 어긋나면 사람마다 화면이 달라진다. 전체 정리 5장의 "서버가 한 번만 계산해 모두에게 같은 화면을 보냄"과도 맞지 않는다 |

## 5. 큰 틀: 바뀌지 않는 이음매

원칙은 하나다. 앞으로 바뀔 것은 전부 이음매 뒤에 두고, 이음매 자체는 오늘 얼린다.

**전체 그림**

```
클라이언트                 서버                       스테이지 프로세스        뇌 프로세스
-----------               -----------                ----------------        -----------
입력 스레드  --사건-->     접속자 읽기
                          게임 마스터  --입력, 틱-->  실행기
                                                      | stage.h
                                                      스테이지 코드
                                                      | brain.h
                                                      뇌 창구  <--공유 메모리-->  모델(가짜/진짜)
수신 스레드  <--화면--     접속자 쓰기  <--칸 그림, 점수--  실행기
렌더 스레드: 합성 -> 터미널
```

- 미니게임의 그림은 서버 쪽 스테이지 프로세스가 그린다. 서버는 중계만 하고, 3분할 배치와 터미널 출력은 클라이언트가 한다.
- 보스전만 클라이언트가 직접 그린다. 서버는 위치와 체력 같은 상태만 보낸다(전체 정리 10장, 24장과 같다).

**이음매 아홉 개**

| 이음매 | 이쪽은 저쪽을 모른다 | 그래서 바뀌어도 되는 것 |
|---|---|---|
| `stage.h` | 스테이지 코드는 누가 자기를 부르는지 모른다 | 혼자 실행, 봇, 서버가 띄운 프로세스 |
| `brain.h` | 스테이지와 보스는 뇌가 무엇인지 모른다 | 가짜 뇌, 진짜 뇌, 큰 시간 간격, 부분 회로, 반응표, 뇌가 죽었을 때의 대체 |
| `ui.h` | 그리는 코드는 픽셀이 어디로 가는지 모른다 | 픽셀 형식, 전송 방법, 이펙트를 입히는 위치 |
| `screen.h` | 화면 코드는 상태가 어디서 오는지 모른다 | 통신 메시지, 미리보기용 예시 상태 |
| 설정 파일 | 코드는 숫자를 모른다 | 난이도, 게임 구성과 순서, 시간 |
| 폴더가 곧 등록 | 빌드는 스테이지 이름을 모른다 | 스테이지 추가, 교체, 삭제 |
| 메시지 틀 | 틀은 메시지 내용을 모른다 | 보스전, 관전, 재접속용 메시지 |
| 틱 | 게임은 벽시계를 모른다 | 실시간 실행, 화면 없이 빨리 돌리기, 같은 입력으로 다시 돌리기 |
| 논리 화면 240×134 | 그리는 코드는 터미널을 모른다 | 터미널 종류, 출력 최적화 |

**네 가지 규칙**

1. **스테이지는 불리는 대로만 움직인다.** 스테이지 코드는 입출력을 하지 않고, 달라지는 것은 스테이지를 감싼 실행기뿐이다. 혼자 돌릴 때와 서버가 띄울 때 같은 실행 파일을 쓴다.
2. **게임의 시간은 틱이다.** 한 틱은 50ms이고, 게임과 뇌와 이펙트가 모두 틱 수로 센다. 실제 시계는 틱 만들기, 감시와 시간 제한, 측정, 클라이언트의 표시에만 쓰고 게임 결과에는 넣지 않는다.
3. **한 가지 일은 한 곳에만 있다.** 일곱 함수를 부르는 루프, `brain.h` 세 함수의 정의, 터미널을 켜고 끄는 코드, 키와 마우스를 해석하는 코드는 각각 한 파일에만 있고 모든 실행 파일이 그것을 같이 쓴다.
4. **약속은 추가만 한다.** 배포한 뒤 팀원용 헤더에는 함수 추가, 구조체 끝에 필드 추가, 열거형 끝에 항목 추가만 한다. 있던 것을 바꾸거나 지워야 하면 팀 전체에 먼저 알리고 한 번에 한다.

## 6. 팀원과의 약속: v6에서 고치는 점

부록 A(팀 명세서 v6)를 고친 것이 v7이다. 함수 개수와 큰 모양은 v6 그대로이고, 대부분은 주석 한 줄이나 필드 하나다. 팀원이 아직 코드를 쓰지 않은 오늘이 이름과 서명을 바꿀 수 있는 마지막 날이라서, 바꿀 것은 전부 여기서 바꾼다.

### 6.1 무엇을 왜 고치나

**이름** ★

| v6 | v7 | 이유 |
|---|---|---|
| `KEY_LEFT`, `KEY_A`, `KEY_B`, `KEY_1` | `SK_LEFT`, `SK_ACT`, `SK_SUB`, `SK_1` | 리눅스 헤더 `<linux/input.h>`에 같은 이름이 다른 값으로 있다(직접 확인: 순서에 따라 컴파일 오류가 나거나 값이 조용히 바뀐다). `KEY_A`가 A 키가 아니라 스페이스라는 점도 헷갈린다 |
| `SUGAR`, `ESCAPE`, `FORWARD` 등 | `BR_SUGAR`, `BR_ESCAPE`, `BR_FORWARD` 등 | `ESCAPE`, `FEED`, `FORWARD`는 스테이지가 자기 상태 이름으로 쓰기 쉬운 말이라 겹치면 컴파일 오류가 난다 |
| `make screen NAME=lobby` | `make screen SCREEN=lobby` | WSL에서 `NAME`은 컴퓨터 이름이 든 환경 변수다. 값을 안 주면 컴퓨터 이름이 화면 이름으로 들어간다 |

**`stage.h`**

| 고치는 점 | 이유 |
|---|---|
| 부르는 규칙을 헤더 맨 위에 적는다(스레드 하나, 프로세스 하나가 한 판, 한 판의 틱 수, `t`의 기준) | v6에는 "한 번", "초당 20번"뿐이라 담당마다 다르게 가정한다 |
| 시간은 틱 수(정수)로 센다. `stage_ctx_t`에 한 판의 틱 수 `n_ticks`를 넣는다 | 0.05를 실수로 400번 더하면 정확히 20이 되지 않아 판의 끝을 놓친다 |
| `player`는 0부터 빈 번호 없이 온다 | 탈락자가 생긴 라운드에서 접속 자리 번호가 그대로 오면 배열 밖에 쓴다 |
| `stage_result`는 언제든 여러 번 불리는 조회 함수다 | 아래 띠에 진행 중 점수를 보이려면 코어가 매 틱 불러야 한다 |
| 점수의 약속을 둔다: 0 이상, 클수록 좋음, 한 판을 잘하면 100 근처 ★ | 단위가 없으면 스테이지 하나가 랭킹을 좌우하고, 0~1 사이의 점수는 반올림에서 사라진다 |
| 키를 누르고 있으면 자동 반복이 계속 온다. 코어는 같은 참가자의 같은 키를 한 틱에 한 번만 넘긴다 | v6의 "꾹 누름은 없다"는 터미널에서 지킬 수 없다. 반복 속도는 노트북마다 다르다 |
| 이동은 "누를 때마다 한 걸음"으로 만든다 | 반복 속도에 기대면 난이도가 기기마다 달라진다 |
| `stage_pointer` 좌표는 0~93, 0~107을 코어가 보장한다. 마우스를 쓰지 않으면 이 함수는 만들지 않아도 된다 | 경계에서 -1이나 108이 오면 배열 밖을 읽는다 |
| `fly` 칸의 그림은 `player`와 무관해야 한다 | 초파리 칸은 모두에게 같은 그림이 간다 |
| `speed`는 스테이지가 곱하지 않는다. 판의 끝은 `ctx->n_ticks`로 안다 | 스테이지마다 다르게 곱하면 라운드 배율을 켜는 날 네 스테이지를 다시 손본다 |
| `stage_info`의 문구 길이 제한(제목은 한글 8자, 규칙은 한글 14자씩 두 줄, 조작은 한글 14자. 영문은 그 두 배) | 시프봇의 말풍선과 화면 띠에 들어가는 길이에 맞춘다 |
| 난수 `stage_rng_*`를 준다. `rand()`, `srand()`, `time()`은 쓰지 않는다 | 진행 속도가 다른 초파리와 유저가 `rand()` 한 줄기를 나눠 쓰면 "같은 문제"가 깨진다 |
| `cfg_get`을 `stage.h`에 선언한다. 없는 키를 읽으면 로그에 경고를 남긴다 | v6에는 어느 헤더인지 없고, 오타가 조용히 기본값으로 돈다 |
| `printf` 금지를 "화면에 직접 쓰지 않는다"로 바꾼다. `printf`와 `fprintf(stderr)`는 로그 파일로 간다 | 금지만 있고 디버그할 길이 없었다 |

**`brain.h`**

| 고치는 점 | 이유 |
|---|---|
| 뇌의 값은 `stage_tick` 직전에 한 번 고정된다. 같은 틱 안에서는 몇 번 읽어도 같다 | 읽는 시점에 따라 값이 달라지면 같은 씨앗에서 같은 결과가 나오지 않는다 |
| `brain_stimulate`는 그 틱에만 유효하다. 같은 집단을 여러 번 부르면 마지막 값 | v6의 "tick마다 다시 불러야 유지"를 정확히 한 것 |
| `brain_rate`의 "최근 50ms"를 지운다. 평균 구간은 뇌 쪽이 집단마다 정하고, 스테이지는 다시 평균 내지 않는다 | 방향 전환 뉴런은 0.2~0.4초 평균이 필요하다(전체 정리 18장) |

| `brain_*`는 멈추지 않고 항상 범위 안의 값을 준다. 뇌가 죽었을 때의 대체는 뇌 창구가 맡는다 | 스테이지마다 대체 규칙을 만들지 않게 한다 |
| 두 뇌가 함께 지키는 반응 표를 둔다(6.3) | 가짜 뇌로 맞춘 스테이지가 진짜 뇌에서도 같은 구조로 돌아야 한다 |
| 가짜 뇌를 빠른 것과 느린 것 두 가지로 둔다 | 방향 전환은 도주보다 늦게 오른다. 빠른 가짜 뇌에만 맞추면 진짜 뇌에서 구조가 안 맞는다 |
| 거미줄 미로에서 냄새 자극을 뺀다 ★ | 냄새 회로는 탐침에서 쓸 만하지 않았다(전체 정리 18장). 전진은 기본 속도로 낸다(11/24: `BR_FORWARD`는 읽지 않기로 했다. 14장) |
| 새 집단은 열거형 맨 끝에만 추가한다 | 중간에 끼우면 번호가 밀린다 |

### 6.2 `stage.h` (v7)

스테이지 하나는 C 파일 하나 이상과 설정 파일 하나다. 아래 일곱 함수를 구현한다.

```c
/* 부르는 규칙
 *  1. 일곱 함수는 한 스레드에서 차례로만 불린다. 시그널 처리기에서는 불리지 않는다.
 *  2. 프로세스 하나가 한 판이다. stage_start는 프로세스마다 한 번만 불린다.
 *     그래서 static 변수를 써도 되고, 처음 상태로 되돌리는 코드는 필요 없다.
 *  3. stage_info는 stage_start보다 먼저 불릴 수 있다.
 *  4. stage_start는 READY GO 전에 불린다. 첫 stage_tick 전에도 stage_draw가 불릴 수 있다.
 *  5. stage_tick은 한 판에 정확히 ctx->n_ticks번 불린다. dt는 항상 STAGE_TICK_DT다.
 *  6. 입력(stage_input, stage_pointer)은 GO 뒤부터 마지막 stage_tick 전까지만 온다.
 *     그 사이에 들어온 입력이 도착한 순서대로 먼저 불리고, 그다음 stage_tick이 한 번 불린다.
 *  7. 시간은 틱 수(정수)로 센다. 초가 필요하면 틱 수 * STAGE_TICK_DT로 구한다.
 *     시계를 읽거나 sleep하지 않는다.
 *  8. stage_draw와 stage_result는 몇 번이든 불릴 수 있고 상태를 바꾸지 않는다.
 *  9. 문제는 ctx->seed에서만 만든다. rand, srand, time을 쓰지 않고 stage_rng_*를 쓴다.
 * 10. 소켓, 스레드, fork, 파일 쓰기를 쓰지 않는다. 화면에 직접 쓰지 않는다.
 *     printf와 fprintf(stderr, ...)는 화면이 아니라 로그 파일로 간다. */

#include <stdint.h>
#include "ui.h"                    /* 각 헤더는 필요한 것을 스스로 포함한다 */

#define STAGE_MAX_PLAYERS 8        /* 유저별 배열의 크기. 지금 게임은 최대 3명 */
#define STAGE_TICK_DT     0.05     /* 초 */

typedef struct {
    const char *title;      /* 게임 이름. 한글 8자(영문 16자)까지. 예: "거미줄 미로" */
    const char *rule;       /* 시프봇이 말해 주는 규칙. 두 줄까지('\n'으로 나눔), 한 줄에 한글 14자까지 */
    const char *controls;   /* 조작 한 줄. 한글 14자까지. 예: "마우스" */
} stage_info_t;

typedef struct {
    int      n_players;     /* 이번 판 참가자 수. 1 이상이고 판 도중 바뀌지 않는다 */
    uint32_t seed;          /* 문제 생성용 씨앗. 초파리와 모든 유저가 같은 문제를 받는다 */
    float    duration;      /* 판 길이(초). 참고용이다. 판의 끝은 n_ticks로 안다 */
    float    speed;         /* 지금은 항상 1.0. 스테이지는 곱하지 않는다 */
    int      n_ticks;       /* 이번 판에 stage_tick이 불리는 횟수. 400을 직접 쓰지 않는다 */
} stage_ctx_t;              /* stage_start가 받은 ctx는 프로세스가 끝날 때까지 유효하다 */

typedef struct {
    float score[STAGE_MAX_PLAYERS];   /* score[i]는 player i의 점수. 0 이상, 클수록 좋다 */
    float fly_score;                  /* 초파리 점수 */
} stage_result_t;

enum {
    SK_NONE = 0,
    SK_LEFT, SK_RIGHT, SK_UP, SK_DOWN,   /* 방향키 또는 A, D, W, S */
    SK_ACT,                              /* 스페이스(주 행동) */
    SK_SUB,                              /* F(보조 행동) */
    SK_1, SK_2, SK_3, SK_4, SK_5, SK_6, SK_7, SK_8, SK_9
};

const stage_info_t *stage_info(void);
void stage_start  (const stage_ctx_t *ctx);
void stage_input  (int player, int key, double t);   /* t: 지금까지 불린 stage_tick 횟수 * STAGE_TICK_DT */
void stage_pointer(int player, int x, int y, int pressed);   /* 마우스를 쓰지 않으면 만들지 않아도 된다 */
void stage_tick   (double dt);
void stage_draw   (int player, canvas_t *fly, canvas_t *me);
void stage_result (stage_result_t *out);

/* 설정. stages/이름/config.ini에서 읽는다. 없는 키는 fallback을 주고 로그에 경고를 남긴다 */
float cfg_get(const char *key, float fallback);

/* 난수. 상태를 직접 들고 있으므로 초파리용, 유저용을 따로 둘 수 있다 */
typedef struct { uint64_t s; } stage_rng_t;
void     stage_rng_seed (stage_rng_t *r, uint32_t seed);
uint32_t stage_rng_u32  (stage_rng_t *r);
float    stage_rng_float(stage_rng_t *r);              /* 0.0 이상 1.0 미만 */
int      stage_rng_range(stage_rng_t *r, int lo, int hi);   /* lo 이상 hi 이하 */
```

| 약속 | 내용 |
|---|---|
| 번호 | `player`는 항상 0부터 `n_players`-1까지 빈 번호 없이 온다. 접속 자리와 무관하다. `score[i]`도 같은 번호다 |
| 유저별 상태 | 유저마다 따로 둔다. 배열 크기는 `STAGE_MAX_PLAYERS`로 잡는다. static 변수는 유저별 배열이거나, 모두에게 같은 일정이거나 둘 중 하나다 |
| 유저끼리 | 참가자의 결과는 다른 참가자의 입력에 영향받지 않는다. 각자 초파리와 겨룬다 |
| 입력 | 키를 누른 순간마다 온다. 뗀 순간은 오지 않는다. 누르고 있으면 터미널의 자동 반복이 같은 `key`로 계속 온다(시작 지연과 간격은 노트북마다 다르다). 코어는 같은 참가자의 같은 `key`를 한 틱에 한 번만 넘긴다. 쓰지 않는 `key`는 무시한다. `SK_NONE`은 오지 않는다 |
| 이동 | 이동은 누를 때마다 정해진 거리의 한 걸음으로 만든다. 걸음 사이의 최소 간격을 유저별로 두고 그 값을 `config.ini`에 둔다. 누르는 동안만 움직이는 조작은 만들지 않는다 |
| 한 번만 반응하는 조작 | 스테이지가 틱 수로 최소 간격을 두고 그 값을 `config.ini`에 둔다 |
| 마우스 | 내 칸 위에 있을 때만 불린다. x는 0~93, y는 0~107을 코어가 보장한다. 좌표가 몇 픽셀씩 변하는지는 가정하지 않는다. 중간 위치는 생략될 수 있으므로 직전 좌표와의 직선으로 처리한다. `pressed`는 왼쪽 버튼이 눌려 있는 동안 1이다. 방향키로도 같은 조작이 되게 한다 |
| 초파리 진행 | `stage_tick` 안에서 `brain.h`로 자극을 주고 반응을 읽어 초파리 칸의 상태를 바꾼다 |
| 그리기 | 캔버스의 이전 내용은 남아 있지 않다. 매번 전부 그린다. `fly`와 `me`는 항상 NULL이 아니다. `fly`에 그리는 내용은 `player`와 무관해야 한다(모두가 같은 초파리 칸을 본다) |
| 점수 | `stage_result`는 조회 함수다. 지금까지의 점수를 채우기만 한다. 코어가 `*out`을 0으로 채운 뒤 매 틱 불러 아래 띠에 보여 주고, 마지막 틱 뒤의 값이 최종 점수다. 띠에 보이므로 칸 안에 점수를 따로 그리지 않아도 된다 |
| 점수의 크기 | 0 이상이고 클수록 좋다. 한 판을 잘하면 100 근처가 되도록 `config.ini`로 맞춘다 ★. 1점보다 작은 차이는 판정에서 사라진다 |
| 길이와 빠르기 | 판의 끝은 `ctx->n_ticks`로 안다. `ctx->speed`는 지금 항상 1.0이고 스테이지는 곱하지 않는다 |
| 통과와 순위 | 스테이지는 점수만 낸다. 통과, 탈락, 랭킹은 코어가 처리한다 |

- 같은 씨앗으로 초파리와 유저가 같은 문제를 받게 하려면, 참가자마다 `stage_rng_t`를 따로 두고 같은 씨앗으로 시작하거나 `stage_start`에서 문제를 미리 다 만든다. 예제 스테이지가 이 방식을 보여 준다.
- 나중에 선택 함수가 필요해지면 코어가 기본 구현을 가진 채로 추가한다. 그래서 이미 만든 스테이지는 고치지 않아도 링크된다.

### 6.3 `brain.h` (v7)

```c
typedef enum {
    /* 입력(자극) */
    BR_SUGAR, BR_BITTER, BR_SALT, BR_WATER,
    BR_LOOM_L, BR_LOOM_R,
    BR_ODOR_L, BR_ODOR_R,
    BR_REPEL_L, BR_REPEL_R,
    /* 출력(반응): 스테이지용 */
    BR_FEED, BR_ESCAPE,
    BR_TURN_L, BR_TURN_R,        /* 좌, 우로 돌려는 정도 */
    BR_FORWARD,                  /* 앞으로 가려는 정도 */
    /* 출력(반응): 보스전용 */
    BR_BACKWARD, BR_LAND, BR_AROUSAL,
    /* 출력(반응): 카드 암기 스테이지용 */
    BR_VALENCE,
    BRAIN_GROUP_COUNT            /* 새 항목은 이 줄 바로 앞에만 추가한다 */
} brain_group_t;

void  brain_stimulate(brain_group_t in, float level);   /* 0.0~1.0. 그 틱에만 유효 */
float brain_rate     (brain_group_t out);               /* 0.0~1.0 */
int   brain_fired    (brain_group_t out);               /* 기준 이상인 동안 1 */
```

| 약속 | 내용 |
|---|---|
| 부르는 곳 | `brain_*`는 `stage_tick` 안에서만 부른다 |
| 값이 고정되는 때 | 뇌의 값은 `stage_tick` 직전에 한 번 고정된다. 같은 틱 안에서는 `brain_rate`와 `brain_fired`를 몇 번 불러도 같은 값이다 |
| 자극 | `brain_stimulate`는 그 틱에만 유효하다. 다음 틱에 다시 부르지 않으면 0이 된다. 같은 집단을 한 틱에 여러 번 부르면 마지막 값이 남는다 |
| 반응이 나오는 때 | 이번 틱에 준 자극의 반응은 빨라야 다음 틱에 보인다 |
| `brain_rate` | 뇌 쪽이 집단마다 정한 구간으로 평균한 값이다. 스테이지는 다시 평균 내지 않는다 |
| `brain_fired` | 그 틱의 반응이 뇌 쪽 기준 이상이면 1이다. 자극이 이어지면 계속 1이다. 한 번만 반응해야 하면 스테이지가 자기 쿨다운을 두고 그 값을 `config.ini`에 둔다 |
| 고장 | `brain_*`는 멈추지 않고 항상 범위 안의 값을 준다. 뇌가 죽었을 때의 대체는 뇌 창구가 맡는다. 스테이지는 대체 규칙을 만들지 않는다 |
| 자극의 종류 | 스테이지는 아래 표에서 자기 줄에 있는 자극만 쓴다. 다른 자극이 필요하면 먼저 말한다 |

쿨다운을 쓰는 예:

```c
if (brain_fired(BR_ESCAPE) && since_flap >= cfg_get("flap_cooldown", 0.25f)) flap();
```

| 스테이지 | 주는 자극 | 읽는 반응 |
|---|---|---|
| 음식 골라 먹기 | `BR_SUGAR`(단것), `BR_BITTER`(쓴것), `BR_SALT`(짠것). 음식은 모양이 보이게 그린다 | `brain_fired(BR_FEED)` |
| 파리채 피하기 | `BR_LOOM_L`, `BR_LOOM_R` | `brain_fired(BR_ESCAPE)`, 방향은 `BR_TURN_L`, `BR_TURN_R` |
| 플래핑 플라이 | `BR_LOOM_L` + `BR_LOOM_R` | `brain_fired(BR_ESCAPE)` |
| 거미줄 미로 | `BR_LOOM_L`, `BR_LOOM_R` | `brain_rate(BR_TURN_L)`, `brain_rate(BR_TURN_R)`. 전진은 `config.ini`의 기본 속도로 내고 `BR_FORWARD`는 읽지 않는다(11/24) |

**두 뇌가 함께 지키는 반응.** 가짜 뇌는 첫 배포부터 이 표를 지키고, 진짜 뇌는 이 표에서 벗어나면 뇌 쪽에서 맞춘다. 스테이지는 이 표에 있는 성질에만 기댄다.

| 자극 | 반응 | 근거 |
|---|---|---|
| 없음 | `BR_FORWARD`만 1이고 나머지 출력은 0 | 전체 정리 18장 |
| `BR_LOOM_L`만 | `BR_TURN_R`이 켜지고 `BR_TURN_L`은 0. `BR_ESCAPE`는 자극이 셀수록 크다 | 18장 |
| `BR_LOOM_R`만 | `BR_TURN_L`이 켜지고 `BR_TURN_R`은 0. `BR_ESCAPE`는 같다 | 18장 |
| 양쪽 `BR_LOOM`이 비슷하게 | `BR_TURN_L`, `BR_TURN_R` 둘 다 0 근처. `BR_BACKWARD`가 켜진다 | 18장 |
| 양쪽 `BR_LOOM`의 세기가 다를 때의 방향 | 미확인 ★. 11/23 전에 탐침으로 확인한다 | 18장의 한계 |
| 양쪽 `BR_LOOM`일 때의 `BR_ESCAPE` | 미확인 ★. 가짜 뇌는 둘 중 큰 값에 따라 한쪽일 때와 같게 낸다. 플래핑 플라이가 여기에 기댄다 | 전체 정리 32장 |
| `BR_SUGAR` | 일정 세기를 넘어야 `BR_FEED`가 켜진다 | 18장 |
| `BR_SUGAR` + `BR_BITTER` | 쓴맛이 셀수록 `BR_FEED`가 줄어든다 | 18장 |
| `BR_BITTER`만 | `BR_FEED`는 0 | 18장 |
| `BR_SALT` | 약한 짠맛(Ir94e 뉴런)이다. `BR_FEED`를 줄인다. 단맛이 아주 세면 그래도 조금 먹는다. 원 논문(Shiu 등 2024)에 나온 반응이고, 우리 탐침으로는 아직 돌려 보지 않았다 ★ | Shiu 등 2024 |
| 신맛 | 쓰지 않는다. 뇌 데이터에 신맛 뉴런이 따로 표시돼 있지 않다 | 전체 정리 6장 |
| `BR_WATER` | 미확인 ★. 가짜 뇌에서는 단맛보다 약하게 `BR_FEED`를 올린다. 지금 스테이지에서는 쓰지 않는다 | 탐침 표에 물이 없음 |
| `BR_FORWARD` | 대응 뉴런이 없다. 두 뇌가 같은 식으로 만든다: 1에서 `BR_LOOM_L`과 `BR_LOOM_R` 중 큰 값을 뺀 것. 스테이지는 기본 속도를 따로 둔다 | 19장 |
| 반응이 오르는 빠르기 | `BR_ESCAPE`와 `BR_FEED`는 자극을 준 다음 틱부터 오른다. `BR_TURN_*`은 평균 구간 때문에 4~8틱에 걸쳐 오른다 | 18장 |
| `BR_ODOR_*`, `BR_REPEL_*` | 반응을 보장하지 않는다 | 18장: 냄새 회로는 쓸 만하지 않았음 |

- **가짜 뇌는 두 가지다.** 빠른 것은 모든 반응이 다음 틱에 나오고, 느린 것은 위 표의 빠르기를 따른다. `make bot`은 둘 다 돌린다. 느린 쪽에서만 초파리 점수가 0에 가까우면 숫자가 아니라 구조의 문제다.
- **파리채 피하기에 주는 영향.** 한 틱에 한쪽만 자극한다(파리채가 초파리의 왼쪽이면 `BR_LOOM_L`, 오른쪽이면 `BR_LOOM_R`). 양쪽을 같이 주면 방향이 0이 된다. 방향은 도주보다 늦게 오르므로, `BR_TURN_L`과 `BR_TURN_R`의 차이가 작으면 그 틱에는 정하지 않고 다음 틱에 다시 본다.
- **거미줄 미로에 주는 영향.** 통로에서는 좌우 벽이 둘 다 가깝다. 양쪽 자극을 그대로 주면 방향 전환이 꺼질 수 있으므로, 더 가까운 쪽만 주거나 좌우 차이만 자극으로 준다. 전진은 `config.ini`의 기본 속도로 낸다. 전체 정리 A.3.2의 "속도는 전진 정도에 비례"와 A.3.8의 "기본 속도 + `BR_FORWARD`에 비례"는 쓰지 않는다(11/24). `BR_FORWARD`는 배선에서 나온 반응이 아니라 두 뇌 모두 "1 - 다가옴 중 큰 값"이라는 규칙으로 만든 값이라서, 읽지 않아도 잃는 뇌 반응이 없다.
- 카드 암기용 학습 함수는 지금 넣지 않는다. 11/22 밤에 넣기로 정하면 그때 함수와 가짜 뇌 구현을 한 번에 추가한다. 추가이므로 이미 쓴 스테이지 코드는 바뀌지 않는다.
- `brain_silence`(끈끈이)는 보스 코드 안에서 처리한다. 필요해지면 보스전용 구역에 함수 하나를 추가한다.

| 스테이지가 그리는 크기 | 항상 `PANE_W`×`PANE_H` 한 가지. 다른 사람 칸은 코어가 절반으로 줄인다. 절반에서도 보이도록 캐릭터와 함정은 4픽셀 이상으로 그린다 |
| 좌표 | 칸의 왼쪽 위가 (0, 0). 캔버스 밖 좌표와 음수 좌표는 `ui_*`가 잘라낸다. 죽지 않는다 |
| 글자 | 글자는 픽셀로 그린다. 문자열은 UTF-8이다. 한글, 영문 대문자, 숫자, 공백, 그리고 `' ! ? / : . , - + % ~`를 그린다. 소문자는 대문자로 바뀌고 없는 글자는 빈칸이 된다. 영문과 숫자는 6×8칸, 한글은 12×12칸을 차지한다. 가로 길이는 `ui_text_w`로 얻는다 |
| 그림의 위치와 크기 | `ui_sprite`의 (x, y)는 그림의 왼쪽 위다. 크기와 프레임 수는 조회 함수로 얻고 숫자로 쓰지 않는다. `SPR_FLY_*` 네 장은 같은 크기다. `frame`은 프레임 수로 나눈 나머지를 쓴다 |
| 그림 불러오기 | 스테이지는 `stage_start`에서 부르고, 화면 함수는 불릴 때마다 불러도 된다. 같은 이름은 같은 번호를 돌려주고 두 번째부터는 파일을 읽지 않는다. 파일이 없거나 틀리면 죽지 않고 `SPR_MISSING`(눈에 띄는 대체 그림)을 돌려주고 로그에 이유를 남긴다 |
| 이펙트를 부르는 곳 | 사건이 난 틱에 `stage_tick`, `stage_input`, `stage_pointer`에서 부른다. `stage_draw`에서는 부르지 않는다. `fx_trail`은 움직이는 동안 매 틱 부른다 |
| 이펙트의 시간 | 지속 시간은 코어가 틱 단위로 센다(50ms 단위로 올림). 초파리 칸에 건 이펙트는 모두에게 보인다 |

**그림 파일** (`stages/이름/assets/*.spr`, 화면은 `screens/assets/*.spr`)

```
; swatter.spr : 줄 하나가 픽셀 한 줄, 글자 하나가 색 이름표
size 8 6
frames 2
palette . C_NONE  b C_FLY_BODY  e C_FLY_EYE  w C_WING
..ww.ww.
.wwbbbww
..ebbe..
..bbbb..
..bbbb..
...bb...
........
.wwwwww.
..ebbe..
..bbbb..
..bbbb..
...bb...
```

- `size W H`는 한 프레임의 크기다. `frames N`은 없어도 되고, 없으면 1이다. 픽셀 줄은 H×N줄을 위에서 아래로 잇는다.
- `;`로 시작하는 줄은 주석이다. 머리 부분의 모르는 줄은 무시한다. 줄 끝의 CR은 버린다(윈도우 편집기로 저장해도 된다).
- 틀린 파일은 `파일:줄: 이유` 형식으로 로그에 남는다(줄 길이가 W와 다름, 모르는 색 이름, 줄 수가 모자람).

### 6.5 `screen.h` (v7)

코어가 상태를 채워서 넘기면 화면 함수가 그린다. 이 화면들은 전체 240×134를 쓴다.

```c
typedef struct { char name[16]; int ready; int ping_ms; int is_host; } lobby_player_t;

typedef struct {
    int n; lobby_player_t p[8];
    int me;                    /* 보는 사람의 줄 번호. 관전자이거나 목록에 없으면 -1 */
    double t;                  /* 이 화면이 뜬 뒤 흐른 초 */
} lobby_state_t;

enum { NEXT_ROUND = 0, NEXT_SPECTATE = 1, NEXT_BOSS = 2 };

typedef struct {
    int n; char name[8][16]; float score[8];
    int passed[8];             /* 이번 라운드에서 초파리를 이겼으면 1 */
    float fly_score; const char *stage_name;
    int lives[8];              /* 이번 판정을 반영한 뒤 남은 기회 */
    int next[8];               /* 다음에 가는 곳. NEXT_* */
    int me; double t;
} round_result_t;

typedef struct {
    int n; char name[16][16];
    int total[16];             /* 코어가 계산한 정수 점수 */
    char best_stage[16][32];   /* 가장 잘한 스테이지의 제목 */
    int me; double t;
} ranking_t;

typedef struct { char watching[16]; double t; } spectate_state_t;

void screen_lobby   (canvas_t *full, const lobby_state_t *s);

void screen_ranking (canvas_t *full, const ranking_t *r);
void screen_spectate(canvas_t *full, const spectate_state_t *s);
```

| 약속 | 내용 |
|---|---|
| 순수한 그리기 | 화면 함수는 받은 상태만 그린다. 상태를 바꾸지 않고, static 변수와 시계 읽기를 쓰지 않는다. 움직임과 깜빡임은 `t`로만 계산한다 |
| 호출 주기 | 화면이 떠 있는 동안 초당 20번까지 반복해서 불린다 |
| 판정 화면 | 목록은 이번 라운드에 뛴 사람이다. 화면은 승패를 다시 계산하지 않고 `passed`를 그대로 쓴다. 점수는 코어가 반올림한 정수로 판정하고 그 값을 넘긴다 ★ |
| 랭킹 화면 | 랭킹 파일에 쌓인 기록이다. 코어가 `total`이 큰 순서로 정렬해서 넘긴다. i번째 줄이 i+1등이다 |
| 관전 화면 | 코어가 관전 대상의 시점으로 띠를 포함한 화면을 전부 그린 뒤 마지막에 `screen_spectate`를 부른다. 이 함수는 `ui_clear`를 부르지 않고 테두리와 안내 글자만 덧그린다 |
| 방장 표시 | `is_host`는 표시용이다 |
| 닉네임 | 영어와 숫자 15자까지 ★. 클라이언트를 실행할 때 인자로 받는다 |
| 필드 추가 | 새 필드는 구조체 끝에만 추가한다. 그래서 이미 쓴 화면 코드는 그대로 컴파일된다 |

- 보스전이 끝난 뒤의 승리와 패배 화면은 서진석이 보스 코드 안에서 직접 그린다 ★. 김고은에게 맡기게 되면 그때 `screen.h`에 함수를 하나 추가한다.
- 뼈대에는 글자만 찍는 기본 화면 네 개가 코어에 들어 있다. `screens/` 안에 같은 이름의 함수를 만들면 그쪽이 쓰인다. 그래서 화면을 하나씩 만들어도 빌드가 깨지지 않는다.

### 6.6 실행 명령, 설정 파일, 완료 기준, 폴더 규칙

**혼자 돌려 보기**

| 명령 | 하는 일 |
|---|---|
| `make run STAGE=swat` | 서버 없이 스테이지 하나를 실제 3분할 화면으로 실행한다. 가짜 뇌. 0번은 키보드와 마우스, 1번과 2번은 무작위 입력 |
| `make run STAGE=swat SEED=7 PLAYERS=1` | 같은 문제로 다시, 한 명만 |
| `make bot STAGE=swat` | 화면 없이 무작위 입력으로 1명, 2명, 3명 판을 여러 번 돌린다. 종료 코드가 0이면 통과 |
| `make screen SCREEN=lobby` | 화면 하나를 예시 상태로 띄운다. `CASE=2`처럼 다른 예시를 고를 수 있다 |

`make bot`이 통과라고 하는 조건:

- 모든 판이 정상 종료한다. 판마다 새 프로세스로 돌리고, 10초 안에 끝나지 않으면 실패다.
- 점수가 0 이상의 유한한 숫자다.
- 같은 씨앗으로 두 번 돌리면 점수가 같다(가짜 뇌 기준).
- 초파리 칸의 그림이 참가자마다 다르지 않다.
- 유저끼리 섞이지 않는다. 3명 판에서 각자의 점수가, 같은 입력으로 혼자 돌린 판의 점수와 같다.
- 그리기와 점수 조회를 틱마다 몇 번 부르든 점수가 같다.
- 로그에 경고가 없다(없는 설정 이름, 불러오지 못한 그림, 너무 긴 문구).
- 메모리 검사와 정의되지 않은 동작 검사에 걸리지 않는다(8.2의 개발용 옵션).

터미널은 240×67칸 이상으로 맞춘다. 글자를 줄이거나 전체 화면으로 바꾸면 된다. 더 작으면 게임 대신 안내가 뜬다(7.5).

**설정 파일** (`stages/이름/config.ini`)

- 난이도에 영향을 주는 숫자는 코드에 쓰지 않고 여기에 둔다. 진짜 뇌로 바꾼 뒤 숫자만 고쳐 균형을 맞추기 위해서다.
- 한 줄에 `이름 = 숫자`. 이름은 영어 소문자, 숫자, 밑줄. `;` 뒤는 주석. 줄 끝의 CR은 버린다.
- 없는 이름을 읽으면 `cfg_get`이 기본값을 주고 로그에 경고를 남긴다.

**스테이지 완료 기준** (v6의 일곱 개에서 4번을 고치고 8번을 더함)

1. `make run`으로 규칙 카드부터 `ctx->duration`초 게임, 판정까지 돌아간다.
2. 초파리 칸에서 초파리가 뇌 반응으로 움직이고, 내 칸에서 내가 조작한 대로 움직인다.
3. `stage_result`가 유저 점수와 초파리 점수를 낸다.
4. `make bot STAGE=이름`의 종료 코드가 0이다.
5. 난이도 숫자가 전부 `config.ini`에 있다.
6. 맞거나 성공하는 순간에 이펙트가 하나 이상 들어간다.
7. 자기 폴더 밖의 파일을 고치지 않았다.
8. 3명 실행에서 세 칸이 서로 다르게 움직인다.

**화면 완료 기준** (새로 둠)

1. `make screen`의 모든 예시에서 죽지 않고 글자가 화면을 넘지 않는다.
2. 상태를 바꾸지 않고 시계를 읽지 않는다.
3. 자기 폴더 밖의 파일을 고치지 않았다.

**폴더 규칙 보완**

- 전체 정리 A.2의 표에 없는 것(루트의 `Makefile`, `.gitignore`, `.gitattributes`, 예제 스테이지 폴더, `docs/`, `tests/`)은 서진석 소유다. README는 김고은이 고친다.
- 새 스테이지 폴더는 팀장이 표에 한 줄을 추가한 뒤 만든다. 카드 암기로 정해지면 `stages/card/`가 김고은 줄에 들어간다.
- 7번 기준은 `main`에 합칠 때 `git diff --name-only main...브랜치`로 확인한다.
- 배포한 뒤 `include/`의 팀원용 헤더는 추가만 한다(5장의 규칙 4).

## 7. 코어 내부의 틀

여기는 팀원이 보지 않는 쪽이다. 팀원 코드에는 영향이 없지만, 코어가 이 위에 쌓이므로 코드를 쓰기 전에 정한다. 전체 정리 24장의 구조를 그대로 두고 빈 곳을 채운 것이다.

### 7.1 프로세스와 스레드: 누가 무엇을 가지는가

| 실행 파일 | 스레드 | 하는 일 | 혼자만 만지는 것 |
|---|---|---|---|
| `server` | 시그널 스레드 | 시그널을 기다렸다가 사건으로 넘긴다 | 없음 |
| | accept 스레드 | 접속을 받는다 | listen 소켓 |
| | 접속자 읽기 스레드(접속마다) | 메시지를 읽어 사건으로 넘긴다 | 그 소켓의 읽기 |
| | 접속자 쓰기 스레드(접속마다) | 보낼 것을 꺼내 쓴다 | 그 소켓의 쓰기 |
| | 게임 마스터 스레드 | 사건을 하나씩 처리한다 | 게임 상태, 자식 프로세스, 파이프 |
| | 감시 스레드 | 뇌가 답하는지 보고, 멈추면 사건을 넘긴다 | 없음 |
| `stage_이름` | 하나 | 실행기 루프(7.2) | 스테이지 상태 |
| `brain_proc` | 하나 | 틱 번호가 오르면 50ms어치를 계산한다 | 뇌 상태 |
| `client` | 입력 스레드 | 키와 마우스를 읽어 사건으로 만든다 | 터미널 입력 |
| | 수신 스레드 | 서버 메시지를 읽는다 | 소켓의 읽기 |
| | 렌더 스레드 | 합성하고 터미널에 쓴다 | 터미널 출력 |

- 게임 상태를 바꾸는 스레드는 게임 마스터 하나다. 나머지는 사건을 넣기만 한다.
- 틱은 게임 마스터가 만든다. 게임 마스터가 기다리는 곳은 `poll` 하나다. 사건 큐를 깨우는 `eventfd`와 스테이지 파이프를 함께 보고, 다음 틱 시각까지만 기다린다(단조 시계). 스테이지 파이프를 `read`로 막힌 채 기다리지 않는다. 그렇게 하면 스테이지 하나가 멈출 때 서버 전체가 멈춘다.
- SIGALRM은 스테이지가 답하지 않을 때의 감시에 쓴다. 울리면 시그널 스레드가 사건으로 넘기고, 게임 마스터가 스테이지를 죽인다.

### 7.2 스테이지 실행기

- 실행 파일은 스테이지마다 하나다. `build/stage_이름` = 실행기(`core/stage_host.c`) + `stages/이름/*.c` + 화면 라이브러리 + 뇌 창구.
- 일곱 함수를 부르는 루프는 실행기 안에 하나만 있다. 바뀌는 것은 앞단 세 가지다.

| 앞단 | 쓰는 곳 | 입력이 오는 곳 | 그림이 가는 곳 |
|---|---|---|---|
| 터미널 | `make run` | 키보드, 마우스, 무작위 입력(1번, 2번 참가자) | 합성해서 터미널로 |
| 무작위 입력 | `make bot` | 씨앗으로 만든 키와 마우스 좌표 | 검사만 하고 버림 |
| 파이프 | 서버가 띄울 때 | 서버가 보낸 입력과 틱 | 서버로 |

한 틱에 실행기가 하는 일(순서 고정):

```
1. 그 사이에 들어온 입력을 stage_input, stage_pointer로 넘긴다
2. 뇌의 값을 한 번 떠서 고정한다
3. stage_tick(0.05)
4. 이번 틱의 자극을 확정해 뇌로 보내고, 뇌 시간을 한 틱 전진시킨다
5. stage_result로 점수를 읽는다
6. 참가자마다 stage_draw를 부르고, 칸 그림에 이펙트를 입힌다
7. 칸 그림과 점수를 앞단으로 넘긴다
8. 이펙트의 남은 시간을 한 틱 줄인다
```

- **파이프 앞단의 약속.** 서버가 "입력들, 그리고 틱 하나"를 쓰면 실행기는 "프레임 하나"로 답한다. 한 번에 하나씩 주고받으므로 실행기 안에는 타이머도 시그널도 없다.
- 서버와의 통로는 물려받은 전용 fd 두 개다. 스테이지의 표준 출력과 표준 오류는 `build/logs/stage_이름.log`로 돌린다. 그래서 스테이지의 `printf`가 통로를 망가뜨리지 않는다.
- 스테이지 폴더의 위치(설정 파일, 그림 파일)는 실행기가 환경 변수로 받는다.
- 스테이지가 2초 안에 답하지 않으면 서버가 죽이고, 그 라운드는 무효로 한다(7.6).

### 7.3 통신 규격 (`protocol.h`)

메시지 머리는 한 가지이고, 소켓과 스테이지 파이프가 같이 쓴다.

```c
typedef struct {
    uint32_t len;     /* 머리 뒤에 오는 내용의 길이. 상한을 넘으면 접속을 끊는다 */
    uint8_t  type;    /* 메시지 종류. 모르는 종류는 len만큼 건너뛴다 */
    uint8_t  flags;
    uint16_t slot;    /* 보낸 사람 또는 대상의 자리 */
} msg_hdr_t;          /* 리틀 엔디언, 8바이트 */
```

| 규칙 | 내용 |
|---|---|
| 버전 | 첫 메시지 `HELLO`에 규격 버전과 닉네임을 싣는다. 버전이 다르면 서버가 이유를 알리고 끊는다 |
| 쓰는 주체 | 소켓 하나에 쓰는 스레드는 하나다(접속자 쓰기 스레드) |
| 두 부류 | 순서대로 다 가야 하는 메시지(로비, 단계 전환, 판정, 랭킹, 보스 사건)는 접속자별 큐에 넣는다. 최신 것만 있으면 되는 메시지(화면, 보스 상태)는 접속자별로 한 칸만 두고 덮어쓴다 |
| 느린 접속자 | 큐가 넘치면 그 접속만 끊는다. 다른 사람의 화면은 멈추지 않는다 |
| 화면 메시지 | 앞 화면에 기대지 않는 완결된 그림이다. 칸마다 같은 색이 이어지는 길이로 줄여서 보낸다. 중간에 들어온 관전자도 다음 화면부터 바로 본다 |
| 입력 메시지 | 클라이언트는 해석만 한 원시 사건(키 코드, 화면 좌표, 반복 여부)을 올린다. `SK_*`로 바꾸고 칸 기준 좌표로 바꾸는 일은 서버가 한다 |
| 소켓 설정 | `TCP_NODELAY`. 서버는 모든 주소에서 받고 포트를 인자로 받는다 |

처음에 둘 메시지는 접속(`HELLO`, `WELCOME`), 로비 상태, 준비와 시작, 단계 전환, 입력, 화면, 판정, 랭킹, 핑이다. 보스전 메시지는 11/24에 같은 틀 위에 더한다.

### 7.4 뇌 연결

- `brain.h`의 세 함수는 `brain/` 안의 한 파일에만 정의한다. 그 뒤에 뇌가 둘 중 하나로 붙는다.

| 붙는 방식 | 쓰는 곳 | 내용 |
|---|---|---|
| 같은 프로세스 안의 모델 | `make run`, `make bot`의 기본값 | 가짜 뇌를 실행기에 링크한다. 지연은 틱 수로 세고, 난수는 씨앗에서 뽑는다 |
| 뇌 프로세스 | 서버 | 공유 메모리로 자극과 반응을 주고받는다 |

- 진짜 뇌(11/22 추가): 실제 배선(FlyWire v783)을 `brain/lif.c`가 계산한다. `make run BRAIN=real`은 같은 프로세스 안에서, 서버는 뇌 프로세스에서 계산한다. 한 틱 계산은 보통 1~10ms, 최대 약 18ms였다(`make brainprobe`로 잰다).

- **뇌 시간은 게임 틱 시간이다.** 자극은 틱 끝에 한 번에 확정되고, 반응 값은 틱 경계에서만 바뀐다. 실행기가 부르는 코어 전용 함수는 둘이다: 판을 시작할 때의 초기화(씨앗 설정), 틱마다의 전진. 이 둘은 `brain.h`에 넣지 않는다.
- **공유 메모리의 약속**

| 항목 | 내용 |
|---|---|
| 주인 | 서버가 만들고 지운다. 서버 없이 돌릴 때는 그 부모가 한다. 뇌와 스테이지는 환경 변수로 받은 이름에 붙기만 한다 |
| 머리 | 식별값, 배치 버전, 재시작 횟수 |
| 게임 쪽이 쓰는 칸 | 판 번호, 씨앗, 틱 번호, 집단별 자극. 판 번호가 바뀌면 뇌가 상태를 처음으로 되돌린다 |
| 뇌 쪽이 쓰는 칸 | 계산을 마친 틱 번호, 집단별 반응 |
| 읽기 | seqlock으로 읽되 재시도 횟수를 끊고, 넘으면 직전에 읽은 값을 쓴다. 멈추지 않는다 |
| 실시간으로 돌 때 | 다음 틱 직전에 뇌가 그 틱을 마쳤는지 본다. 못 마쳤으면 직전 값을 쓰고 밀린 틱 수를 기록한다 |
| 화면 없이 빨리 돌 때 | 뇌가 그 틱을 마칠 때까지 기다린다(시간 제한을 두고, 넘으면 직전 값을 쓴다). 그래서 초파리가 반응하지 않은 채 검사가 통과하는 일이 없다 |

- 뇌 프로세스 안의 모델도 갈아 끼운다. 가짜 모델로 띄우면 배선 파일 없이도 공유 메모리, 감시, 재시작을 시험할 수 있다. 진짜 모델은 배선 바이너리를 `mmap`해서 쓴다.
- 속도 대비책(큰 시간 간격, 부분 회로, 반응표)은 모두 뇌 프로세스 안에서 한다. 공유 메모리와 감시는 그대로 둔다.
- 뇌가 죽으면 서버가 `waitpid`로 알고, 죽지는 않았는데 멈춘 것은 감시 스레드가 알아낸다. 어느 쪽이든 게임 마스터가 다시 띄운다. 다시 띄우기 전에 뇌 쪽 칸을 정리하고 재시작 횟수를 올린다. 그동안 뇌 창구는 직전 값을 유지하고, 길어지면 가짜 모델로 바꾸되 그 사실을 화면과 로그에 드러낸다 ★(바꾸는 시점은 11/28~29에 정한다).
- 집단마다 어떤 뉴런이 속하는지는 코드가 아니라 데이터 파일에 둔다. 뇌가 뜰 때 집단별로 찾은 뉴런 수를 찍고, 0이면 실패한다. 먹기 회로의 뉴런 번호는 v630에서만 확인됐으므로 v783 기준으로 다시 확인한다.

### 7.5 화면 한 줄기

```
캔버스(색 번호 격자)  ->  합성(칸 배치, 절반 축소, 위아래 띠)  ->  표시(반칸 블록, 바뀐 칸만, write 한 번)
```

- 캔버스는 1바이트 색 번호의 격자다. 스테이지 칸은 94×108, 전체는 240×134다. 색 번호를 RGB로 바꾸는 표는 표시 단계에만 있다.
- 합성과 표시는 클라이언트, `make run`, `make screen`이 같은 코드를 쓴다.
- 보스전의 3D도 같은 전체 캔버스에 그린다. 거리에 따른 밝기는 색 표에 밝기 단계를 두어 낸다.

**크기 정책: 줄이지 않는다** ★

| 터미널 크기 | 동작 |
|---|---|
| 240×67칸보다 작다 | 게임 대신 안내만 띄운다(지금 몇 칸인지, 글자를 줄이거나 전체 화면으로 하라는 말). 접속은 유지하고, 커지면 전체를 다시 그린다 |
| 240×67칸 이상 | 1배로 가운데에 놓고 남는 칸은 배경색으로 채운다 |

- 전체 정리 11장의 "최소 160×45칸, 최대 320×90칸"을 바꾸는 결정이다. 분수 배율로 줄이면 1픽셀 두께의 거미줄 벽과 픽셀 글씨가 깨지고, 화면에는 뚫린 길인데 판정은 닿음이 된다.
- FHD 화면 전체를 쓴다면 글자 한 칸이 8×16픽셀일 때 240×67칸이다. 실제로는 창 테두리, 탭 줄, 여백이 칸을 차지하므로 글자를 한 단계 더 줄여야 할 수 있다(미확인). 그래서 이 정책을 확정하기 전에, 세 사람이 각자 터미널을 전체 화면으로 하고 글자를 줄인 뒤 `stty size`로 67줄 240칸 이상이 나오는지 먼저 본다. 발표 화면도 11/22 무렵까지 같은 방법으로 본다. 모자라는 화면은 글자를 더 줄여 맞추고, 축소 규칙은 만들지 않는다.
- 팀장 노트북(2880×1800)에서 잰 값: 기본 글자 크기에서는 전체 화면이 148칸 47줄이라 모자란다. `Ctrl`+`-`를 다섯 번 누르면 전체 화면에서 256칸 80줄, 최대화한 창에서 256칸 73줄이 된다. 네 번 누르면 216칸이라 모자란다.
- 크기가 바뀌면(SIGWINCH) 표시만 세우고, 렌더 스레드가 터미널 크기를 다시 읽는다.

**터미널을 켜고 끄는 코드는 한 곳에 둔다.** 원시 입력 모드, 대체 화면, 커서 숨김, 마우스 보고(1003, 1006)를 켜고, 끝날 때 되돌린다. 정상 종료뿐 아니라 죽을 때도 되돌린다. `make run`은 프로그램이 끝난 뒤 셸에서 한 번 더 되돌린다. 키와 마우스를 해석하는 코드도 한 곳이다.

### 7.6 게임 마스터의 상태 기계

- 단계는 `LOBBY`, `CARD`, `READY`, `PLAY`, `VERDICT`, `BOSS`, `RANK`다. 단계마다 마감 시각을 가진다.
- **진행자와 화면 흐름은 UI 구상안대로 한다.** 진행자는 칼리코 고양이 "시프봇"이고 말풍선으로 안내한다. 흐름은 입장 화면(파티장 앞에서 시프봇이 인사, 입장과 지난 랭킹 보기와 나가기), 라운드 소개(`CARD` 단계: 시프봇이 그 게임의 `rule`을 말해 준다, 3초), 카운트다운(`READY` 단계: 3, 2, 1, GO, 2초 ★), 게임, 판정, 그리고 마지막의 1등 시상이다. 시프봇 장면은 코어가 그리고, 그림은 구상안을 색 블록 픽셀 그림으로 옮긴다.
- **색은 아직 확정하지 않았다.** 구상안의 7색보다 화려하게 가도 된다. 색 번호는 1바이트라 256색까지 늘릴 수 있고, 새 색은 이름표 끝에 추가한다.
- **미니게임은 4종을 모두 한다. 4라운드이고 순서만 무작위다.** 파리채 피하기와 닿으면 안 되는 미로는 강연우, 음식 골라 먹기(단것, 쓴것, 짠것)와 플래핑 플라이는 김고은이 맡는다.
- **4라운드를 거친 뒤 대왕 초파리 보스전을 한다.** 아이템은 파리채(기본), 스프레이(장거리), 끈끈이(투척, 초파리를 잠시 무력화)다. 초파리의 공격은 단순 공격과 날개 파동이다.
- 단계가 바뀔 때 클라이언트에 메시지 하나를 보낸다(어느 단계인지, 마감까지 얼마인지, 규칙 카드 문구, 남은 기회).
- 게임 마스터에 들어오는 사건은 접속과 끊김, 클라이언트 메시지, 틱, 스테이지의 답, 자식 프로세스 종료, 뇌 멈춤이다. 시연용 운영자 명령(단계 건너뛰기 등)이 필요해지면 사건 종류 하나로 더한다.

정상 흐름은 전체 정리 A.1의 흐름도 그대로다. 비어 있던 곳의 기본값은 아래와 같다 ★.

| 상황 | 기본값 |
|---|---|
| 참가와 관전 | 접속한 순서로 3명까지 참가자다. 그 뒤에 들어온 사람과 판이 진행 중일 때 들어온 사람은 관전자다 |
| 시작 | 참가자 전원이 준비(`SK_ACT`)한 상태에서 방장이 `SK_SUB`를 누르면 시작한다. 방장은 가장 먼저 들어온 참가자이고, 나가면 다음 참가자다. v6의 "전원 준비면 자동 시작"은 첫 접속자가 혼자 준비해도 시작돼 버린다 |
| 판정 | 점수를 반올림한 정수로 비교한다. 같거나 높으면 WIN |
| 아래 띠 | 이번 게임의 내 점수와 초파리 점수, 남은 기회 |
| 참가자가 라운드 도중 끊김 | 라운드는 계속한다. 그 사람은 그 라운드를 진 것으로 한다 |
| 4라운드가 끝나기 전에 전원이 기회를 잃음 | 남은 라운드를 건너뛰고, 그때까지 점수가 가장 높은 1명이 보스전에 간다. 참가자가 0명인 판은 시작하지 않는다 |
| 참가자 전원이 접속을 끊음 | 로비로 돌아간다 |
| 누적 점수 | 라운드마다 반올림한 점수를 더한다 |
| 스테이지가 결과 없이 죽거나 멈춤 | 그 라운드는 무효다(기회 변화 없음). 아직 안 나온 게임에서 다시 뽑는다 |
| 다시 하기 | 준비를 모두 지우고, 빈 참가 자리를 접속한 순서로 채운다 |

- 스테이지 목록과 고정 순서는 팀장 소유의 한 곳에 이름 목록으로 둔다(서버 인자 `--order=swat,food,web`). 팀원용 `cfg_get`은 숫자 전용이므로 쓰지 않는다.
- **기회는 3번이다.** 라운드에서 초파리에게 지면 1개가 줄고, 0이 되면 관전으로 넘어간다.
- 라운드 수, 기회 수, 단계 길이는 서버와 `make run`이 함께 쓰는 한 곳에 둔다.

### 7.7 서버가 지키는 세 가지 규칙

1. **시그널.** `main`이 첫 스레드를 만들기 전에 SIGCHLD, SIGALRM, SIGINT, SIGTERM을 막는다. SIGPIPE는 무시한다. 시그널 처리기는 두지 않고, 시그널 스레드 하나가 `sigwaitinfo`로 받아 게임 마스터에 사건으로 넘긴다.
2. **자식의 주인.** `fork`, `execve`, `waitpid`와 자식의 pid, 파이프는 게임 마스터 스레드만 다룬다. 감시 스레드는 뇌가 멈췄다는 사건만 보낸다. SIGCHLD는 여러 개가 하나로 합쳐질 수 있으므로, 자식 종료 사건마다 `waitpid`를 더 없을 때까지 부른다.
3. **fd와 exec.** 모든 fd는 exec 때 닫히게 만든다(`O_CLOEXEC`, `SOCK_CLOEXEC`, `pipe2`, `accept4`). 자식은 `fork`와 `execve` 사이에 시그널 마스크 초기화, SIGPIPE를 기본 동작으로 되돌리기, 부모가 죽으면 같이 죽게 하는 설정(`prctl`), 통로 fd의 닫힘 표시 풀기, 표준 출력과 표준 오류를 로그로 돌리기, `execve`, `_exit`만 한다. 통로 fd는 번호를 옮기지 않고 그 번호를 인자로 넘긴다(`dup2`는 두 번호가 같으면 아무 일도 하지 않아 닫힘 표시가 남는다). 부모는 띄운 직후 자식 쪽 파이프 끝을 닫는다.

팀장 노트북의 WSL에서 확인한 것: 자식이 listen 소켓을 물려받은 채 살아 있으면 서버를 다시 띄울 때 주소가 이미 쓰이고 있다는 오류가 난다. 다른 자식이 파이프의 쓰는 쪽을 쥐고 있으면 끝났다는 신호가 오지 않는다. 읽는 쪽이 없는 파이프에 쓰면 SIGPIPE로 죽는다. 세 규칙은 이 셋을 막는다.

### 7.8 보스전이 오늘의 틀에 요구하는 것

보스전은 3D 1인칭 슈팅이다. 둠 느낌의 화면을 계산이 가벼운 방식(레이캐스팅: 화면의 세로줄마다 광선 하나)으로 그린다. 11/24에 시작하지만, 아래는 오늘 만드는 통신과 입력에 걸려 있어서 지금 정한다 ★.

1. **보스전도 서버가 주인이다.** 클라이언트는 미니게임과 같은 입력 사건만 올린다. 서버의 보스 계산이 초당 20번 전원의 위치, 방향, 체력을 내려보내고, 클라이언트는 두 상태 사이를 이어서 그린다. 이동은 누를 때마다 한 걸음, 한 각도다.
2. **입력 스레드는 합치기 전의 사건을 넘긴다.** W, A, S, D를 방향키와 합치는 일은 스테이지로 넘길 때만 한다. 보스전은 합치기 전의 키를 쓴다. 사건에는 반복 여부와, 나중에 키를 뗀 순간을 알 수 있게 되면 쓸 자리를 둔다.
3. **보스 코드는 둘로 나눈다.** 입출력이 없는 계산부(서버, 봇, 훈련이 같이 씀)와 클라이언트의 그리기다. 혼자 3D는 같은 계산부에 참가자 1명을 넣은 것이다.
4. 보스 계산은 서버의 게임 마스터 스레드에서 돈다. 체력 0, 전멸, 180초 중 먼저 오는 때에 끝난다.
5. 관전자는 같은 상태를 받아 관전 대상의 시점으로 그린다.

## 8. 폴더, 빌드, 개발 환경

### 8.1 폴더

```
include/          stage.h brain.h ui.h screen.h (팀원용), protocol.h (코어용)
core/             실행기(stage_host.c), 서버, 클라이언트, 공용 코드(설정, 로그, 메시지)
ui/               캔버스, 그리기, 글자, 그림, 이펙트, 합성, 표시, 터미널, 입력 해석
brain/            brain.h 세 함수의 정의, 가짜 모델, 공유 메모리, 뇌 프로세스, 진짜 모델
boss/             보스 계산부, 보스 그리기
stages/example/   예제 스테이지 (서진석)
stages/swat/  stages/web/     강연우
stages/food/  stages/flap/    김고은
screens/          김고은
tools/            봇 실행, 화면 미리보기, 터미널 속도 측정, 배선 변환(파이썬)
tests/            자동 검사
docs/             이 설계서, 팀원 안내
build/            빌드 결과와 로그 (git에 넣지 않는다)
data/             배선 바이너리, 랭킹 파일 (git에 넣지 않는다)
```

전체 정리 26장의 폴더 구성 그대로이고, `tests/`, `docs/`, `build/`, `data/`를 더했다.

### 8.2 빌드 규칙

| 규칙 | 이유 |
|---|---|
| 스테이지는 폴더 이름으로 찾는다. `stages/이름/*.c`를 전부 묶어 `build/stage_이름`을 만든다 | 새 폴더를 넣으면 Makefile을 고치지 않고 `make run STAGE=이름`이 돈다 |
| `screens/*.c`도 자동으로 묶는다 | 위와 같다 |
| 스테이지와 화면의 목적 파일은 보관 파일(.a)로 묶지 않고 그대로 링크한다 | 기본 구현을 덮어쓰는 방식(6.5)은 목적 파일로 링크할 때만 동작한다 |
| Makefile은 상대 경로만 쓴다 | 경로에 공백이나 대괄호가 있으면 절대 경로가 깨진다(아래 확인) |
| 헤더 의존성을 추적한다(`-MMD -MP`) | 헤더가 바뀌면 그 헤더를 쓰는 파일이 전부 다시 빌드된다 |
| 개발용 옵션은 한 벌이다: `-std=gnu11 -Wall -Wextra -g -O1 -fno-omit-frame-pointer -fsanitize=address,undefined -fno-sanitize-recover=undefined`. 링크에는 항상 `-lm` | 메모리 오류를 첫날부터 잡는다. 나중에 켜면 끝냈다고 한 코드가 떨어진다 |
| 시연용 빌드(`make release`)만 `-O2`에 검사 없이 만든다 | 뇌 속도 |
| make에 주는 값은 `STAGE`, `SEED`, `PLAYERS`, `SCREEN`, `CASE`, `BRAIN`이다. 환경 변수에서 온 값은 쓰지 않는다 | 6.1의 `NAME` 문제 |

### 8.3 줄바꿈과 파일 이름

| 규칙 | 이유 |
|---|---|
| `.gitattributes`에 `* text=auto eol=lf`를 넣는다 | 팀장 노트북의 윈도우 git은 줄바꿈을 CRLF로 바꾸게 설정돼 있다. 그대로 두면 설정 파일과 그림 파일 줄 끝에 `\r`이 붙는다 |
| 설정 파일과 그림 파일을 읽는 코드는 줄 끝의 CR을 버린다 | 윈도우 편집기로 저장한 파일도 읽히게 한다 |
| 심볼릭 링크를 쓰지 않는다. 대소문자만 다른 파일 이름을 만들지 않는다 | 윈도우 쪽에서 깨진다 |
| 스크립트는 실행 권한에 기대지 않고 `sh tools/이름.sh`로 부른다 | 윈도우 쪽에서는 실행 권한이 저장되지 않는다 |

### 8.4 작업 위치 ★

팀장 노트북에서 확인한 것(2026-11-21):

| 항목 | 값 |
|---|---|
| 저장소가 있는 파일 시스템 | 윈도우 쪽(`/mnt/c/...`), WSL에서는 9p로 보인다 |
| 지금 경로에서 make의 `$(CURDIR)` | 공백 때문에 세 조각으로 나뉜다 |
| 지금 경로에서 절대 경로로 파일 찾기 | 대괄호 때문에 빈 값이 나온다. 상대 경로로는 찾는다 |
| WSL의 git으로 본 상태 | 고치지 않은 README가 바뀐 것으로 나온다(줄바꿈 차이) |

- **기본값: 팀장도 작업 사본을 WSL 홈의 공백 없는 경로에 둔다**(예: `~/2026_sysprog`). 전체 정리 14장이 팀원에게 정한 것과 같은 규칙이다. 이렇게 하면 위 표의 문제가 모두 사라진다.
- 옮기기 전까지는 윈도우 쪽 사본을 고치고, 빌드와 실행은 WSL 홈에 복사해서 한다.
- 실행 중에 만드는 파일(로그, 랭킹, 공유 메모리)은 리눅스 파일 시스템에 둔다. 윈도우 쪽 폴더에서 파일 잠금과 이름 바꾸기가 같게 동작하는지는 미확인이다.
- 여러 대 접속: 서버는 모든 주소에서 받고 포트를 인자로 받는다. 서버 노트북의 WSL 네트워크 설정(미러 방식 또는 포트 전달)은 절차를 `docs/`에 적어 둔다. 현장 망이 막혔을 때를 위해 노트북 한 대에서 서버, 봇 2명, 사람 1명으로 도는 `make demo-local`을 둔다.

## 9. 검증 틀

목표 G6을 위한 틀이다. 검사는 처음부터 켜 두고, 코드보다 늦게 붙이지 않는다.

| 검사 | 무엇을 돌리나 | 무엇을 잡나 | 누가, 언제 |
|---|---|---|---|
| `make bot STAGE=이름` | 스테이지 하나를 화면 없이. 씨앗 여러 개, 1명부터 3명까지, 키와 마우스 좌표(경계 값 포함)를 섞어서 | 죽음, 멈춤, 배열 밖 쓰기, 씨앗이 같은데 결과가 다른 것, 초파리 칸이 사람마다 다른 것 | 담당이 올리기 전에 |
| `make test` | 작은 단위 검사와, 서버에 봇 접속자 2명이 붙어 화면 없이 한 판을 끝까지 가는 검사 | 설정 파일과 그림 파일 읽기, 메시지 틀, 그림을 줄였다가 되살리기, 좌표 자르기, 난수, 접속부터 랭킹까지의 흐름 | 팀장이 `main`에 합치기 전에 |
| 같은 입력으로 다시 돌리기 | 실행기에 들어간 입력을 파일로 남겼다가 다시 넣는다 | 한 번 난 문제를 그대로 다시 만든다 | 문제가 났을 때 |
| 화면을 파일로 | 한 프레임을 그림 파일로 떨군다 | 터미널 없이 화면 모양을 본다 | 필요할 때 |
| `make termbench` | 실제 터미널에 전체 화면을 계속 그리며 초당 프레임 수를 잰다. 마우스 보고도 확인한다 | 터미널이 따라오는지 | 세 명이 각자 노트북에서, 키트가 나온 날 한 번 |
| `make demo-local` | 노트북 한 대에서 서버, 봇 2명, 사람 1명 | 현장 망이 막혔을 때의 시연 경로 | 11/30 리허설 |

**지키는 것**

- 모든 실행 파일에 화면 없이 도는 방식이 있다. 스테이지는 무작위 입력 앞단, 클라이언트는 봇 접속자, 서버는 틱을 기다리지 않고 돌리는 방식이다.
- 가짜 뇌에서는 스테이지, 씨앗, 인원, 입력이 같으면 점수가 같다. 진짜 뇌는 이 보장에서 뺀다.
- 코어, 화면 라이브러리, 가짜 뇌는 전역 `rand()`를 쓰지 않는다. 난수는 모두 씨앗에서 나온다.
- 봇은 판마다 새 프로세스를 띄운다. 6.2의 "프로세스 하나가 한 판"과 같은 조건이다.

**자동 검사로 못 잡는 것.** 실제 터미널의 모양과 프레임 수, 실제 Wi-Fi에서의 여러 대 접속, 재미와 난이도는 직접 해 봐야 안다. 모일 때마다 실제 터미널과 노트북 두 대로 한 판 돌려 본다.

**1단계 통과 기준**

- `make run STAGE=example`이 3분할 화면으로 규칙 카드부터 판정까지 돈다. 0번은 키보드와 마우스, 나머지 둘은 무작위 입력이다.
- `make bot STAGE=example`의 종료 코드가 0이다.
- `make screen`으로 네 화면이 뜬다.
- `stages/example/`을 다른 이름으로 복사하면 다른 파일을 고치지 않고 `make run STAGE=새이름`이 돈다.
- 팀원 두 명이 각자 노트북에서 위 명령을 돌린다.
- 세 노트북에서 `make termbench`로 프레임 수와 마우스를 잰다.

예제 스테이지는 팀원이 베껴서 시작하는 틀이다. 아래를 모두 보여 줘야 한다.

**2단계 통과 기준**

- `make test`에서 서버와 봇 접속자 2명이 화면 없이 로비부터 랭킹까지 간다.
- 사람 2명이 노트북 두 대로 예제 스테이지 한 판을 끝까지 간다(전체 정리 27장의 11/21~22 기준). 휴대폰 핫스팟에서도 해 본다.
- 같은 `build/stage_example`이 `make run`과 서버 양쪽에서 돈다.
- 뇌 프로세스를 `kill -9`로 죽여도 게임이 이어지고 뇌가 다시 뜬다(가짜 모델로).
- 키를 누른 때부터 화면이 바뀔 때까지의 지연을 노트북 두 대로 잰다. 플래핑 플라이와 거미줄 미로가 이 구조로 되는지 여기서 판단한다.

**3단계: 뇌 속도 판정일을 11/23으로 둔다** ★

- 11/23까지 "실시간이 된다, 안 된다"를 숫자로 정한다. 전체 정리의 판단일(11/22, 11/26, 11/29)에 하나를 더하는 것이다.

## 11. 이 틀이 흡수하는 변경과 흡수하지 못하는 변경

**흡수하는 변경.** 아래는 일어나도 팀원이 이미 쓴 코드를 고치지 않는다.

| 앞으로 바뀔 수 있는 것 | 바뀌는 곳 | 조건 |
|---|---|---|
| 가짜 뇌에서 진짜 뇌로 | `brain/` 안. 스테이지는 `config.ini`의 숫자만 | 스테이지가 6.3의 표에 있는 성질에만 기댄다 |
| 뇌가 느려서 큰 시간 간격, 부분 회로, 반응표로 내려감 | 뇌 프로세스 안 | 스테이지가 자기 줄의 자극만 쓴다 |
| 카드 암기가 플래핑 플라이를 대신함 | `brain.h`에 함수 추가, 가짜 뇌, `stages/card/` 추가, 서버의 게임 목록 | 새 항목을 열거형 끝에 추가한다 |
| 네 번째 게임을 뺌, 게임 순서를 고정함 | 서버의 게임 목록 | 없음 |
| 라운드 수, 기회 수, 단계 길이 | 코어의 한 곳 | 스테이지가 `ctx->n_ticks`를 쓴다 |
| 라운드마다 빨라지게 함 | 코어(틱 간격을 줄인다). 뇌가 그만큼 빨라야 해서 뇌 속도 판정 뒤에 정한다 | 스테이지가 `speed`를 곱하지 않는다 |
| 보스를 혼자 3D나 2D로 줄임 | `boss/`의 그리기. 계산부는 그대로 | 서버의 보스 상태가 3D 시점에 묶여 있지 않다 |
| 훈련 결과 파일을 끼움 | `boss/` | 보스전용 출력에만 적용한다. `BR_FEED`, `BR_ESCAPE`, `BR_TURN_*`, `BR_FORWARD`는 바꾸지 않는다 |
| 에어팟, 마우스 직접 읽기 | 클라이언트의 입력 스레드. 사건 종류를 하나 더한다 | 없음 |
| 키를 뗀 순간을 알 수 있게 됨 | 클라이언트의 입력 해석 | 사건에 비워 둔 자리를 쓴다(7.8) |
| 화면 디자인, 초파리 시안 | `screens/`, 코어의 그림 파일 | 스테이지가 그림 크기를 조회 함수로 얻는다 |
| 재접속 | 통신 메시지 추가, 서버의 자리 관리 | 없음 |
| 스테이지에 선택 함수를 추가함 | 코어가 기본 구현을 가진 채로 추가 | 없음 |
| 터미널 출력을 줄여야 함 | 표시 단계 안 | 없음 |

**흡수하지 못하는 변경.** 아래를 바꾸면 팀원 코드를 고쳐야 한다. 그래서 오늘 얼린다.

| 무엇 | 왜 |
|---|---|
| 칸 크기 94×108 | 스테이지의 모든 좌표가 이 크기 기준이다 |
| 틱 길이 0.05초 | 스테이지의 속도와 쿨다운 숫자가 이 기준이다 |
| 일곱 함수의 서명, 키 이름, 뇌 집단 이름 | 모든 스테이지가 쓴다 |
| `brain_fired`의 뜻(기준 이상인 동안 1) | 초파리 쪽 로직이 이것에 기댄다 |

## 12. 정한 것과 정해야 할 것

**이 설계서가 정한 틀.** 팀이 확정하면 이대로 만든다.

1. 순서는 "키트를 끝에서 끝까지의 첫 조각으로"다(4장).
2. 스테이지마다 실행 파일 하나, 앞단은 셋이다(7.2).
3. 미니게임 그림은 서버 쪽 스테이지 프로세스가 그려서 칸 단위로 보낸다. 픽셀은 색 번호 1바이트다(7.3, 7.5).
4. 뇌 시간은 게임 틱 시간이다(7.4).
5. 메시지 머리는 하나, 메시지는 두 부류, 소켓마다 쓰는 스레드는 하나다(7.3).
6. 게임 상태는 게임 마스터만 바꾼다. 서버는 세 규칙을 지킨다(7.1, 7.7).
7. 검사는 첫날부터 켠다(8.2, 9장).

| 보스전은 키보드만 썼다. A와 D로 22.5도씩 돌고 Shift로 살금살금 걸었다 | 마우스를 좌우로 움직이면 시선이 돈다. A와 D는 옆걸음, 왼쪽 클릭은 무기 쓰기, C는 살금살금 켜고 끄기다. 한 걸음은 3틱에 나눠 움직인다. 시선은 클라이언트가 정해 서버에 알린다(입력의 `INPUT_LOOK`) | 팀장 결정(11/24, 직접 해 보고). 서버를 거쳐 돌아온 방향으로 그리면 마우스가 한두 틱 늦다. 통신 규격의 버전을 2로 올렸다 |
| 보스전 화면에는 뇌 표시가 없었다 | 3D 화면 왼쪽 위에 미니게임과 같은 뇌 표시를 놓고, 아래에 자극과 도약 막대를 붙였다. 서버가 `MSG_BOSS`의 상태 뒤에 그 틱의 뇌 값을 붙여 보낸다 | 팀장 결정(11/24). 따로 보내면 "최신 것만" 보내는 칸에서 상태와 서로 밀어내서 한 메시지에 실었다 |
| 화면은 글자 칸(위아래 반칸 문자)으로만 보냈다(11장) | 터미널이 Sixel 그림을 받으면 화면을 픽셀 그림으로 보낸다(`ui/sixel.c`, `ui/hd.c`). 터미널에 물어서 고르고(`term_caps`) 못 받는 터미널에서는 전처럼 글자 칸으로 보낸다. 보스전은 픽셀 그림용으로 따로 그린다(`boss/boss_view_hd.c`: 무늬, 명암, 부드러운 가장자리). 다른 화면은 240x134 그림을 계단을 깎아 키우고 글자만 큰 글꼴(`ui/assets/font48.fnt`)로 다시 그린다 | 팀장 결정(11/24). 글자 칸으로는 5배(1200x670)로 키워도 픽셀처럼 보였다. 한 칸에 색을 둘밖에 못 써서 무늬나 명암을 넣으면 내보내는 양이 감당이 안 된다. Windows Terminal 1.25가 1200x670 그림을 1초에 100장까지 받는 것을 재 보고 정했다. 스테이지와 화면 코드, 팀원용 헤더는 바뀌지 않는다 |
| 화면 배율은 1~4였고 글자도 같은 배율로 커졌다 | 배율은 1~6과 `auto`다. 배율 3 이상에서는 보스전의 글자와 상태 줄을 절반 크기로 그린다. Windows Terminal에서 글자 칸을 2x4픽셀로 줄이는 프로필(`tools/wt_profile.json`)을 둔다 | 팀장 결정(11/24). 2배(480x268)도 픽셀이 크게 보였다. 2560x1440 화면에서 배율 5(1200x670)가 된다 |

**발표 구성으로 잰 성능 (11/24)**

발표용 빌드(`make release`), 진짜 뇌, 참가자 3명(봇 2명과 화면을 그리는 클라이언트 1개), 관찰자 1명, 미니게임 2라운드와 보스전 30초를 한 컴퓨터(8코어, WSL)에서 실시간으로 두 번 돌렸다.

| 잰 것 | 값 |
|---|---|
| 뇌의 한 틱(미니게임) | 평균 1.7~5.3ms, 최대 9.9~13.1ms. 늦은 틱 0, 건너뛴 틱 0 |
| 뇌의 한 틱(보스전) | 평균 0.4ms, 최대 10.7~18.0ms. 600틱 중 늦은 틱 1 |
| 화면이 접속자에게 도착한 수 | 미니게임 400장 중 399~400장, 보스전 600장 중 600장 |
| 화면 사이의 가장 긴 간격 | 52~55ms(틱 간격이 50ms) |
| CPU | 뇌 평균 2.7%(0.5초 구간 최대 21%), 서버 0.7%, 화면 클라이언트 0.4%, 스테이지 0.1% |
| 메모리 | 뇌 92MB, 서버와 클라이언트와 스테이지는 각각 2~3MB |
| 접속자 한 명에게 보내는 양 | 미니게임 초당 60~75KB, 보스전 초당 4KB |
| 화면 클라이언트가 터미널로 내보내는 양 | 초당 74~97KB |

뇌 시간 50ms를 30ms 안에 계산한다는 기준을 넉넉히 지킨다. 서버 쪽에서 더 줄일 곳은 없다.
재지 못한 것: 화면 클라이언트는 출력을 버리는 가짜 터미널에 그렸다. 실제 터미널이 초당 74~97KB를 제때 그리는지는 그 터미널에서 `make termbench`로 본다. 접속자가 모두 같은 컴퓨터에 있었으므로 통신 지연도 재지 않았다.
